## 이번 주 구성

**I2C → SPI → 자체 프로토콜** 순서로 간다.

- **실습 1·2, 문제 1 (I2C)** — 스캐너로 주소를 찾고, LCD를 띄운 뒤, 같은 버스에
  **장치만 바꿔** OLED를 직접 붙인다. 배울 점은 "장치가 바뀌어도 버스 설정은
  같다"와 "**주소를 먼저 확인한다**"이다.
- **실습 3 ① (SPI)** — RC522의 VersionReg(0x37)를 읽어 **SPI 송수신이 되는지만**
  확인한다. SPI 초기화·수동 CS·Dummy byte를 파일 하나에 다 적어, 강의안 §2·§7의
  내용이 그대로 보이게 했다.
- **실습 3 ② (SPI)** — 그 위에 **카드를 올린다.** 드라이버 `mfrc522.c`로 UID를
  읽어 등록 목록과 비교하고, 결과는 전부 시리얼로 찍는다. 서보를 안 쓰므로
  배선을 더하지 않는다 — 도어락(§8.7)에서 `printf` 자리에 `servo_angle()`이
  들어갈 뿐이다. 카드를 "치웠다"고 판단하는 데 **4주차 Debounce**가 다시 나온다.
- **실습 4 (DHT11)** — I2C도 SPI도 아닌 **부품 제조사의 자체 방식**이다. 표준이
  없을 때 어떤 일이 벌어지는지 보여준다. I2C 한 줄로 끝날 일이 100줄이 된다.
- **문제 2 (기상관측기)** — 이번 주의 마무리다. **서로 다른 두 프로토콜을 한
  프로그램에서** 쓴다. 새 개념이 없고 **조합**이라 학생이 직접 쓰기에 알맞다.
  벤더 L23 Mini Weather Station이 하려던 것이기도 하다.

> LCD가 불량인 조는 문제 1을 먼저 하고 실습 2를 건너뛰어도 된다.
> 둘 다 I2C 디스플레이라 배울 내용이 겹친다.

## ⚠️ 실물 확인 결과

교수님 키트로 시험한 결과다. **실습 계획에 영향이 있다.**

| 부품 | 상태 |
| --- | --- |
| I2C 스캐너 | 정상 동작 |
| LCD1602 | **I2C 통신 정상** (0x27로 응답). 3.3V + 대비 조절로 글자 표시 확인(2026-10-20) |
| OLED (SSD1306) | 미확인 |
| DHT11 | 미확인 |
| RFID (MFRC522) | 2026-09-24 기준 **헤더 핀 미납땜**. 실습 3을 하려면 납땜이 필요하다 |

> LCD는 처음에 "전원이 안 들어온다"고 판단했으나, 스캐너가 0x27을 찾아
> **칩과 배선은 정상**임이 확인됐다. 백라이트가 3.3V에서 안 켜져 죽은 것처럼
> 보였던 것이다. 주소도 벤더 기준 0x3F가 아니라 **0x27**(PCF8574T)이었다.

> ⚠️ **실습 3 전에 RC522 헤더 납땜 상태를 확인할 것.** VersionReg가 `0x00`이나
> `0xFF`로 나오면 MISO 단선이나 무응답이다 — 납땜·배선부터 본다.

### OLED를 넣은 이유

| | LCD1602 | SSD1306 OLED |
| --- | --- | --- |
| 전원 | 원래 5V 부품 (3.3V면 흐림) | **3.3V 정상** |
| 신호선 전압 | 백팩 풀업이 VCC로 가서 5V면 GPIO에 걸림 | **3.3V, 문제 없음** |
| 대비 | 가변저항으로 맞춰야 함 | 불필요 |
| 안 보일 때 | 전원·대비·주소 중 뭔지 가리기 어려움 | 켜지거나 안 켜지거나 |

LCD는 "칩은 살아 있는데 화면만 안 보이는" 상태가 가능해서 원인이 얽힌다.
OLED는 그런 중간 상태가 없다.

### ⚠️ OLED는 Read 스캐너에 안 잡힐 수 있다

SSD1306의 Serial interface는 **Write용**이다. 실습 1 스캐너는 주소마다 1-byte
**Read**를 요청하므로 OLED가 응답하지 않을 수 있다. **스캐너에 0x3C가 없다고
미연결·고장으로 판정하지 않는다.** OLED만 연결한 상태에서 NOP Command를 써 보는
것으로 확인한다(강의안 §8.1).

```c
uint8_t probe[] = {0x00, 0xE3};  // Control + NOP
int n = i2c_write_timeout_us(i2c0, 0x3C, probe, sizeof(probe), false, 10000);
printf("SSD1306 command ACK: %s\n", n == sizeof(probe) ? "YES" : "NO");
```

불특정 장치 전체에 이 바이트를 보내지 않는다. ACK가 와도 드라이버 초기화와
실제 표시는 따로 확인한다.

## ⚠️ LCD 전원 — 3V3을 쓸 것 (벤더 문서와 다름)

키트 튜토리얼 **L22는 LCD1602의 VCC를 `VSYS`에 연결**하라고 되어 있다.
**그대로 따르면 안 된다.**

I2C 백팩(PCF8574)의 **풀업 저항은 VCC로 연결**돼 있다. VCC가 5V면 SDA·SCL이
**5V로 풀업**되고, 그 선이 `GP0`·`GP1`에 그대로 들어간다. **RP2040·RP2350의
GPIO는 5V 내성이 없다** — 규격 초과이며 핀이 손상될 수 있다.

7주차 포텐셔미터(L14의 VSYS)와 같은 종류의 문제다.

**이 폴더의 실습은 3V3을 쓴다.**

- 3V3으로 하면 SDA·SCL이 3.3V로 풀업되어 안전하다.
- HD44780은 원래 5V 부품이라 **화면이 흐릴 수 있다.** 백팩의 **대비
  가변저항(파란 사각형)** 을 돌려 조절한다.
- 5V 모듈을 꼭 써야 하면 SDA·SCL에 **양방향 레벨 시프터** 등을 따로 검토한다
  (키트에는 없다). 레벨 시프터 없이 5V로 쓰지 말 것.

## 배선

| 실습 | 부품 | 핀 |
| --- | --- | --- |
| 1·2 | LCD1602 (I2C) | GP0→SDA, GP1→SCL, **3V3**→VCC, GND→GND |
| 문제 1 | SSD1306 OLED | GP0→SDA, GP1→SCL, **3V3**→VCC, GND→GND |
| 실습 3 | RC522 RFID | GP5→SDA(CS), GP6→SCK, GP7→MOSI, GP4→MISO, GP22→RST, **3V3**→3.3V(5V 금지), GND→GND |
| 실습 4 | DHT11 온습도 | **GP15**→DATA(가운데 핀), 3V3→VCC, GND→GND |
| 문제 2 | LCD + DHT11 | 위 둘을 **동시에** (GP0·GP1 + GP15) |
| 참고 (보류) | 서보 | GP0→S(노랑), VCC(빨강), GND→GND(갈색) — 전원은 정격·전류 검토 후 별도 구성 |
| 참고 (보류) | 부저 (선택) | GP14→(+), GND→(−) |

- LCD와 OLED는 **같은 SDA=GP0, SCL=GP1**을 공유하고 주소로 상대를 구분한다.
- RC522(GP4~7, GP22)와 DHT11(GP15)은 I2C 핀과 겹치지 않는다. 그래서 실습 3·4와
  문제 2는 앞의 I2C 배선을 그대로 둔 채 더해 갈 수 있다.
- RFID **도어락**(보류)만 서보가 GP0을 써서 I2C와 함께 배선할 수 없다.
- 9주차 UART 점퍼선이 GP0·GP1에 남아 있으면 스캐너가 멈춘다. 먼저 뺀다.

> 벤더 L23은 DHT11을 GP2에 꽂지만, 이 프로토콜은 전용 하드웨어를 쓰지 않으므로
> **핀은 어디든 상관없다.** I2C(GP0·GP1)·SPI(GP4~7)와 겹치지 않는 자리를 골랐다.
> DHT11 모듈 핀 순서는 **VCC · DATA · GND**라 가운데가 데이터선이다.

RFID 모듈의 `IRQ` 핀은 쓰지 않는다(벤더 배선표도 비워 두었다).

### I2C 풀업과 속도

실습은 RP2040의 **내부 풀업**을 켠다. LCD 백팩에 이미 외부 풀업이 달려 있어
대개 문제없지만, 내부 풀업(50~80kΩ)은 I2C에 약하다(강의안 §3.3). 장치가 안
잡히거나 값이 불안정하면 외부 풀업을 검토한다. **4.7kΩ은 시작값일 뿐**이고,
버스 정전용량과 속도에 따라 계산한다(강의안 §3.5).

**속도는 100kHz로 통일했다.** LCD의 PCF8574는 규격이 **100kHz**라, 같은 버스에
LCD가 있으면 OLED도 100kHz로 써야 한다(주소가 달라도 Clock은 공유). OLED만
단독으로 연결했다면 400kHz도 된다.

## 실습 순서 — 스캐너를 먼저

실습 1(스캐너)을 **반드시 먼저** 돌린다. LCD 주소가 모듈마다 다르기
때문이다(0x27 또는 0x3F). 스캐너로 확인한 주소를 `lab2_lcd_hello.c`의
`LCD_ADDR`에 넣는다.

```c
#define LCD_ADDR 0x27        // 실물 확인값 (PCF8574T). PCF8574AT면 0x3F.
```

아무것도 안 잡히면 드라이버 문제가 아니라 배선·전원·풀업 문제다. 단 OLED는
위에서 말한 대로 Read 스캐너에 안 잡힐 수 있다.

## 직접 작성한 드라이버

`lcd1602.c`, `mfrc522.c`, `dht11.c`는 직접 작성했고, `ssd1306.c`는 **Raspberry Pi
공식 예제를 바탕으로** 했다. 강의안 PPT의 드라이버 발췌(LCD `write_byte`·`strobe`,
MFRC522 `read_reg`, DHT11 수신 루프, TM1637 `tm_write_byte`)는 이 파일들과 같다.

### `lcd1602.c` — HD44780 + PCF8574 백팩

LCD 자체는 병렬 장치인데, 백팩의 PCF8574(I2C → 8비트 출력 확장 칩)가 그
병렬 핀을 대신 흔들어준다. **LCD 자체의 I2C 레지스터에 문자열을 쓰는 구조가
아니다.**

| 비트 | 용도 |
| --- | --- |
| P0 | RS (0=명령, 1=데이터) |
| P1 | RW (항상 0) |
| P2 | EN (스트로브) |
| P3 | 백라이트 |
| P4~P7 | 데이터 4비트 |

핀이 4개뿐이라 한 바이트를 **상위 → 하위 니블** 두 번에 나눠 보내고, 니블마다
EN을 HIGH→LOW로 바꿔 전달한다(4비트 모드). PCF8574에 보내는 바이트는 LCD의
**핀 상태**다. I2C의 ACK와 LCD 명령 완료 여부는 서로 다른 조건이고, 드라이버는
I2C 반환값을 호출부에 전달하지 않는다.

### `ssd1306.c` — OLED (공식 예제 기반)

폰트 데이터와 초기화 순서를 `pico-examples/i2c/ssd1306_i2c/`에서 가져왔다
(Copyright (c) 2021-2022 Raspberry Pi Ltd, **BSD-3-Clause**). 128x32였던 것을
128x64로 맞추고, 버퍼·글자 함수를 이 수업 형태로 정리했다.

폰트는 **16열 × 8행, 대문자 A~Z와 숫자 0~9만** 있다. 소문자는 대문자로 바꿔
표시하고 그 밖의 문자는 공백이 된다.

**① Control byte로 명령과 데이터를 구분한다.** 같은 I2C 주소(0x3C)로 보내면서
D/C# 비트로 구분한다 — 드라이버는 `0x80 + Command`, `0x40 + Frame buffer`.

**② 그리기와 보내기가 나뉘어 있다.** `ssd1306_clear`·`text`·`pixel`은 RAM
버퍼(128×64/8 = 1024바이트)만 고치고, `ssd1306_show()`가 화면 영역을 설정한 뒤
버퍼를 보낸다. 여러 줄을 고친 뒤 show를 한 번만 부르면 전송 횟수가 준다.

> 갱신 시간은 **데이터 1024바이트 × (8비트 + ACK)만 따져도** 100kHz에서 약 92ms,
> 400kHz에서 약 23ms다. 주소·Control·명령 바이트를 더하면 실제 시간은 더 길다.
> show는 Blocking이다. TM1637의 2ms와 비교하면 5주차의 "루프 안에서 하는 느린 일"
> 이야기가 그대로 이어진다.

### `dht11.c` — 표준이 아닌 프로토콜

**이 파일은 이번 주에 열어볼 가치가 있다.** I2C·SPI는 전용 하드웨어가 파형을
만들어주지만, DHT11은 CPU가 직접 시간을 재야 해서 프로토콜이 코드에 그대로
드러난다.

```
시작   MCU가 약 20ms LOW  -> 선을 놓음
응답   센서가 80us LOW, 80us HIGH
데이터 비트마다 약 50us LOW + HIGH 구간
         HIGH 약 23–27us -> 0
         HIGH 약 68–74us -> 1      (드라이버 기준값 50us)
```

- **체크섬** — 5바이트 중 마지막이 앞 네 바이트 합의 하위 8비트다.
- **인터럽트를 잠깐 막는다** — 20ms 시작 LOW는 차단 **밖에서** 기다리고, 응답과
  40비트를 재는 동안만 `save_and_disable_interrupts()`로 막는다. 성공·실패와
  무관하게 `restore_interrupts()`를 부르고, 출력은 복원한 뒤에 한다.
- **정수부만 쓴다** — 바이트 0을 습도, 바이트 2를 온도로 쓰는 단순화 구현이다.
  부품 리비전의 부호·소수 형식은 별도 확인.
- **빨리 물어본다고 빨리 답하지 않는다** — 전원 인가 후 2초 대기, 실습은 2초 간격.

### `mfrc522.c` — RFID 리더

카드가 있는지 묻고(REQA), 있으면 4바이트 UID를 읽어온다(ANTICOLL).
MFRC522의 SPI 주소 규약(데이터시트 8.1.2.3):

```
주소 바이트 = (레지스터 << 1) & 0x7E
읽기는 여기에 0x80을 OR 한다.     <- 이 장치의 규약. 모든 SPI 장치 공통 아님
```

`read_reg()`에서 주소를 보낸 뒤 **Dummy byte를 내보내며 받는** 부분이 강의안
§2.4의 "Read에도 Clock이 필요하다"를 그대로 구현한 것이다. 실습 3의
`lab3_rfid_version.c`는 이 `read_reg()`와 같은 코드를 파일 안에 직접 적었다.

UID를 읽은 뒤 **BCC**(네 바이트의 XOR)를 검증해 잘못 읽은 것을 걸러낸다.

실습 3 ②(`lab3b_rfid_uid.c`)가 이 드라이버를 쓰는 첫 실습이다. 도어락과 다른
점은 **서보가 없다는 것뿐**이고, 등록 카드 비교까지는 같다.

> ⚠️ **하드웨어 검증 필요**: `mfrc522.c`는 빌드·링크만 확인했다. 모듈 헤더가
> 미납땜이라 실습 3 ①·②와 도어락 모두 실물에서 아직 못 돌려봤다. 납땜 후
> Version 확인(①) → 카드 읽기(②) → 도어락 순으로 재검증한다.

## 참고 — RFID 도어락 (보류) 카드 등록하는 법

처음에는 등록된 UID가 더미값(`0xDE 0xAD 0xBE 0xEF`)이라 모든 카드가
거부된다.

1. 빌드해 올리고 시리얼 모니터를 연다.
2. 카드를 대면 `UID: 3A 5F 12 C4` 처럼 찍힌다.
3. 그 값을 `lab6_rfid_door.c`의 `registered[]`에 적어 넣는다.
4. 다시 빌드해 올리면 그 카드가 등록 카드가 된다.

문이 열린 뒤 **3초 후 자동으로 잠긴다.** 잠금 대기는 5주차 논블로킹 tick이다.
서보 분주기는 7주차와 같이 `clock_get_hz(clk_sys)`로 런타임에 계산한다.
서보 전원은 정격과 전류를 검토해 별도로 구성하고 GND를 공통으로 한다.

## 보드 설정

`CMakeLists.txt`에 `PICO_BOARD pico`(RP2040)로 되어 있다.

**Pico 2(RP2350)를 받았다면** 이 줄만 바꾸고 `build` 폴더를 지운 뒤 다시
빌드한다. `PICO_BOARD`는 캐시 변수라 그냥 재빌드하면 예전 값이 남는다.

```cmake
set(PICO_BOARD pico2 CACHE STRING "Board type")
```

> 보드 구분은 칩 위의 각인(`RP2040` / `RP2350`)으로 한다.
> 5주차 `lab1_clock_check`를 올리면 시리얼로도 확인된다.

**I2C·SPI는 두 보드 모두 2개씩 있고 SDK 함수도 같다.** 기본 핀 배치도
동일해 실습 코드는 그대로 동작한다. 도어락(보류)의 서보도 PWM 분주기를
런타임에 계산하므로 두 보드 모두 정확히 50Hz가 나온다.
